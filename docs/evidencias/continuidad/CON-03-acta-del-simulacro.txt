2 · EL SIMULACRO QUE SI PUEDE FALLAR
-----------------------------------------------------------------------------
Se escribio infra/backup/run_restore_drill_postgres.ps1, que sigue la
secuencia de un desastre de verdad:

    1. Respaldar el origen.
    2. Restaurar en una base de ensayo.
    3. ROMPER la base de ensayo a proposito.
    4. Restaurar otra vez desde el respaldo.
    5. Comprobar que lo borrado VOLVIO.

El paso 3 es el que lo convierte en una prueba. Sin el, el paso 5 se cumple
solo.

NUNCA TOCA PRODUCCION. Trabaja contra la base local y restaura en
botica_staging, que se recrea en cada corrida. Las credenciales de Neon no
intervienen, y el script aborta si la base de ensayo coincide con la de
origen.

5 · LO QUE ESTE NUMERO NO DICE
-----------------------------------------------------------------------------
El RTO de 0,93 s se midio sobre una base de 0,16 MB en la MISMA maquina. No es
el tiempo de una recuperacion real, y presentarlo como tal seria enganoso. Lo
que demuestra es que el procedimiento FUNCIONA y que el respaldo es
restaurable; el tiempo crecera con el tamano y con la latencia de red hacia
Neon.

Lo honesto para el informe: el procedimiento esta verificado, el RTO
comprometido tiene margen sobrado para este volumen, y la cifra hay que volver
a medirla si la base crece en un orden de magnitud.

Sobre el RPO de 24 horas: los scripts de respaldo existen y el simulacro
confirma que lo que producen se puede restaurar, PERO LA PROGRAMACION DIARIA
NO ESTA ACTIVA. Mientras nadie ejecute el respaldo a diario, el RPO de 24
horas es una intencion. Es la diferencia entre poder y hacer, y queda anotada
como pendiente en el plan del informe final.
